# Authoring workflow

1. Establish the assignment and writable paths using [parallel ownership](parallel-workflow.md) when other workers are active. Read the complete module, including annotations, exercises and citations; record missing sources. Create or update its curriculum/notation map using [module continuity](module-continuity.md). For ES98A use `es98a-curriculum-map.md`. Work chronologically, recording what earlier chapters establish and later chapters need.
2. Identify learning objectives and the difficult conceptual transition.
3. Propose purposeful interventions with a question, placement, static/interactive decision and mathematical invariants. Prefer static sequences for fixed relationships and focused controls for counterfactuals. The Week 1 visual review supersedes the initial three-figure limit; see the current Week 1 editorial plan.
   Map every major section's question → intuition → formal result → visual role. Rewrite transitions and exposition as needed; a figure must participate in the reasoning. Evaluate the writing separately from whether controls work. Use `week1-editorial-plan.md` as the current example.
4. Reuse primitives; keep topic-specific computation separate from rendering. Do not invent a universal visualisation API.
5. Introduce the figure in surrounding prose, use a stable ID and explain the comparison or experiment in its caption. Restructure prose and local sequencing as needed for clarity; preserve mathematical substance, assumptions, proofs and references, not original wording. Check new component registration before inserting it into live MDX.
6. Test analytic cases, parameter boundaries and invariants. Compile MDX and inspect KaTeX, citations and links.
7. Run desktop/mobile browser checks, inspect screenshots, keyboard/touch and no-JavaScript behaviour. Check both themes and local overflow. Run TypeScript and production build; verify gallery is 404 in production.
8. Update the curriculum map, correction ledger and module handoff. The shared owner updates component reference, pattern catalogue and executable gallery for common API/convention changes; module workers supply concrete proposals. Record actual validation and its limits using [handoff templates](handoff-templates.md).

Commands and their exact scope are in [architecture](architecture.md#validation-and-local-runtime). `npm run test:browser` already builds; avoid a redundant build unless new changes justify it. New numerical test files need explicit execution and shared-owner CI integration. Playwright needs Chromium (`npx playwright install chromium`) and exclusive use of the configured ports/build outputs. No automatic publishing occurs. Once the migration baseline is reconciled, keep shared changes and chronological module checkpoints separate; never stage unrelated changes.
